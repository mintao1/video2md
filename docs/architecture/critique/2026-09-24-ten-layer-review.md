# 批判①：终局布局十层「叙述 vs 现实」对照审查

- **批判对象**：`README.md`「终局布局（云服务器 · 多用户）」十层表（L257–272）及其落地状态小节（L274–287）
- **批判基准**：代码现实（证据精确到 `文件:行号`，核对日期 2026-09-24，HEAD=f6a4a0e）
- **方法**：逐层三栏对照——**叙述**（文档承诺）/ **现实**（代码行为）/ **定级**
- **定级口径**：
  - ✅ **落地** — 叙述与代码一致，证据可复核
  - 🟡 **半档** — 核心机制在，但叙述溢出了实现边界（夸大、缺配套、或依赖人工纪律）
  - ❌ **缺失/矛盾** — 叙述与实现脱节，或同仓两处表述互相打架

---

## 总评

十层中 **2 层全绿（产物、观测告警）、6 层半档、2 层含硬矛盾**。整体印象：这不是一份「吹牛文档」——绝大多数机制真实存在且有测试钉住；问题集中在三类经典病灶：

1. **叙述溢出实现边界**：把「读侧走 PG」说成「任务表 PG 真相源」、把「信号量并发」说成「多 worker 队列调度」——读 README 的运维者会按不存在的语义做容量与故障推演。
2. **关键防线靠「人工纪律」而非「机制」**：`/docs` 关闭、安全组只放 80/443、secrets 手工备份、恢复演练「建议每季度」——全部无代码/无配置实体承载，是写给未来运维者（很可能是凌晨三点的自己）的善意便签。
3. **git 提交措辞与文档出界项互相矛盾**：`3f7bb1a`/`f6a4a0e` 提交信息称「双进程冒烟全绿」，README 同版本却列「多副本冒烟进 CI」为未做出界项——两者只能有一个是真的（见「执行层」详查）。

## 逐层对照

### 1. 入口层 — 🟡 半档

| | 内容 |
|---|---|
| **叙述** | 「域名 + 反代 TLS 是唯一公网入口（SSE 不缓冲；`/docs` `/openapi.json` 网关侧关闭）；安全组只放 80/443，api/算力池/观测栈全回环」（README L263） |
| **现实** | 反代配置**只有 README 内嵌示例**（L121–147），仓内无 nginx/caddy 配置实体，`deploy/` 目录只有观测栈配置；`/docs` `/openapi.json` 在代码里无条件开放（`api.py:620-621`），关闭动作完全依赖运维者手工照抄示例并记得加 deny 规则；「安全组只放 80/443」是文字口径，仓内无任何 IaC/防火墙脚本承载 |
| **定级依据** | 机制本体（`V2MD_HOST=127.0.0.1` 回环绑定，`api.py:1046-1048`；compose `network_mode: host`）真实存在，但「网关侧关闭 /docs」这一安全关键动作无资产、无校验、无测试——教科书定义的 *policy without mechanism* |

**批判**：入口层是公网系统的第一防线，此层的「半档」不在绑定（做对了），而在**把安全关键配置留在文档里**。`deploy.sh`（`scripts/deploy.sh:49-50`）起栈后不验证 `/docs` 是否被反代拦掉——漏配反代 deny 规则的部署会静默裸奔 OpenAPI。企业基线要求：反代配置入仓、版本化、随部署生效、上线检查自动化。

### 2. 鉴权与账目层 — 🟡 半档

| | 内容 |
|---|---|
| **叙述** | acctkit 登录（Google id_token / 设备流 / 微信扫码，provider 可插拔）；run 按 uid 归属——越权 403、dedup 按 owner 隔离（README L264） |
| **现实** | 机制真实且扎实：`_require_run_access` 越权 403（`api.py:283-296`）、acctkit 引擎按序尝试 provider、Google+微信 unionid 归并有测试（`test_acctkit.py`）。**但**：`V2MD_AUTH=off` 是缺省值（`acctkit/providers.py` Fake+Dev 兜底），与 `V2MD_ENV=production`（compose 已配，`docker-compose.yml:56`）可以**共存而系统不抗议**——忘了配 AUTH 的生产部署会以「所有人共享 dev uid」形态裸奔，无任何启动校验拦它 |
| **定级依据** | 鉴权机制本身 ✅；「绝不 off 上公网」目前只是 README L156 检查清单里的一行字，靠部署者自律 |

**批判**：这是**可防呆而未防呆**的典型案例。`config.py` 已有 fail-fast 先例（`V2MD_ARTIFACT_MODE` 非法值直接 raise，`config.py:113-115`），同样的纪律一行代码就能覆盖「production + auth=off」组合，却没做。企业基线：危险配置的非法组合必须在启动期爆炸，而不是在检查清单里祈祷。

### 3. 执行层 — ❌ 含硬矛盾（十层中问题最重）

| | 内容 |
|---|---|
| **叙述** | 「多 worker 并发：**队列调度** + 每用户并发上限 + **公平排队**……任务表 PG 真相源（`V2MD_TASKS_STORE=postgres`……多副本下各实例看到的是同一个队列）」（README L265）；落地状态表称 P4b「全落地」（L280） |
| **现实** | ①「任务表 PG 真相源」是**读侧真相源**：`_TASKS` 写路径仍是进程内 dict（`api.py:230`，代码注释自述「写路径保留不动」`api.py:240-243`）；`GET /runs/{id}` 的 `task` 字段只读本进程内存（`api.py:852-856`）——副本 B 看不到副本 A 驱动的 run 的实时任务段，只能靠 SSE 扇出和 runs 表 status 列补。②「队列调度」不存在：并发控制是一个 `asyncio.Semaphore`（`api.py:231`），无调度器、无优先级、**无公平排队**（FIFO 唤醒序不保证跨用户公平，单用户灌满队列时他人照样排队——`USER_QUEUE_MAX` 限的是数量不是调度公平）。③「多 worker」的真实语义 = 单进程内信号量计数，不是多副本 worker 池 |
| **定级依据** | 叙述三个关键词（队列调度/公平排队/多 worker）全部溢出实现；且 README 自列出界项四条（L282–287）与「P1–P4b 全落地」标题（L274）在同一小节内互相打架 |

**硬矛盾实锤**：提交 `3f7bb1a` 与 `f6a4a0e` 的信息称「真库测试与**双进程冒烟**全绿」；而 `test_pg_stores.py:159-211` 的 events 扇出测试实为**单进程内双实例模拟**（`_simulate_other_proc` 手工 NOTIFY 注入，L182-190），README L287 同期自述「多副本冒烟进 CI（现为一次性脚本，未固化）」。**两个进程从未在同一台机器上互相看见过对方**——P4b 的全部跨进程语义（LISTEN 泵、SKIP LOCKED 认领、steal 接管）只经过单进程双实例与真库 SQL 验证，未经真双进程端到端验证。这不是措辞瑕疵，是验证闭环的缺口。

**批判**：执行层是十层中叙事野心最大、实现最诚实（代码注释把「读侧/写路径」讲得清清楚楚）的一层——**问题不在代码，在文档把代码没说出口的结论说了**。教科书原则：架构文档的每个形容词都要能指到一行代码；「公平」「调度」「真相源」这类有精确定义的词更不能例外。

### 4. 状态层 — 🟡 半档（隐患最深远）

| | 内容 |
|---|---|
| **叙述** | 「Postgres 承载 users / runs / state + checkpointer；单文件 JSON 形态只属开发机」（README L266） |
| **现实** | 三存储分派 + 迁移脚本真实落地（`pgstore.py`、`auth/pg_store.py`、`scripts/migrate_json_to_pg.py`）。**但全库无任何 schema 版本化机制**：建表 DDL 散在各 store 构造函数里（`pgstore.py:40-51, 88-93`；`auth/pg_store.py:32-44`），`claimed_by` 列靠 `ALTER TABLE ... IF NOT EXISTS` 就地补（`pgstore.py:127`），无 `schema_version` 表、无 migrations 目录、无回滚概念、无启动期漂移校验 |
| **定级依据** | 当下能用（绿字段+幂等 DDL 对单库场景足够），但这是**以技术债计息的方式活着**：第一个需要改列/拆 jsonb/加约束的版本到来时，没有任何机制保证「代码版本 ↔ 库结构版本」对齐 |

**批判**：PG 连接池同样裸奔——`pg.py:33-36` 只配了 `min_size=1/max_size=5/autocommit/prepare_threshold=0`，无 `connect_timeout`、无池获取超时、无语句超时：PG 挂起时请求线程会无限期阻塞在池获取上，把「数据库故障」放大成「API 全挂」。企业基线：任何外部依赖的连接必须带超时预算。

### 5. 产物层 — ✅ 落地（唯一全绿的功能层）

| | 内容 |
|---|---|
| **叙述** | deliver「云端不储存」：per-run outbox → bundle 拉取 → ACK/TTL 即焚；上传走专用上传面 + 路径白名单（README L267） |
| **现实** | 与叙述一致且实现诚实：`_outbox_live` 惰性焚（`api.py:438-455`）、`_sweep_outbox` 物理删（`api.py:201-226`）、bundle 现打包发完即删（`api.py:908-937`）、410 语义不掺假；上传面流式落盘 + 单文件上限 + 配额 + TTL（`api.py:666-702`） |

**残余瑕疵**（不降级，记入 ROADMAP）：上传校验只有**后缀白名单**（`api.py:350, 673`），无 magic number/内容嗅探——伪装 `.mp4` 后缀的任意内容可进 uploads 目录，后续喂给 yt-dlp/ffmpeg 的攻击面未被收敛。

### 6. 限流配额层 — ❌ 缺失（半面墙）

| | 内容 |
|---|---|
| **叙述** | 「per-user 限流（**入口/反代层**）+ 磁盘配额 + 队列长度上限」（README L268） |
| **现实** | 应用内三道提交闸真实（`api.py:304-345`，PG 档滑窗 `pgstore.py:291-305`）。**但括号里的「入口/反代层」限流不存在**——无仓内反代配置（见入口层），自然无 `limit_req` 之类的实体；更要命的是**匿名端点完全裸奔**：`POST /auth/device/code` 与 `/auth/device/token`（`api.py:708-739`）不鉴权、不频控，任何公网脚本可无限刷 Google device/code 申请（消耗我方 OAuth 配额、骚扰 Google 侧风控）；`/queue`、`/preflight` 同样无频控 |
| **定级依据** | 叙述承诺的两层限流只落了一层；匿名面（攻击者最感兴趣的入口）恰恰落在没盖的那半面 |

**批判**：限流的第一原则是先盖**匿名面**再盖**认证面**（认证请求已被身份与配额天然约束）。本项目恰好做反了：认证用户的提交闸精致（三种 429 信封齐全），匿名攻击面零防护。

### 7. 算力层 — 🟡 半档

| | 内容 |
|---|---|
| **叙述** | gpu_router 算力池独立伸缩，与 api 解耦——api 侧零 GPU（README L269） |
| **现实** | 解耦真实（api 只是 HTTP 客户端，`V2MD_REMOTE` 指向）；插件协议清晰（`gpu_plugins/v2md/__init__.py:42-65` 能力契约 + `PROVIDER_IMPL` 装载）。**但**：① gpu_router `:9700` **无认证面**——`docker-compose.yml:25-26` 注释自述「无认证不暴露公网」，防线 = 安全组叙述 + 运维者读注释；② `reference/colab_cell_server.py` 的 cloudflared quick tunnel 是**无鉴权公网 URL**（模块自述），知道这个临时域名即可白嫖 GPU 工时 |
| **定级依据** | 架构解耦做对了；安全模型是「网络位置即信任」——在单宿主回环内成立，但 quick tunnel 把这个模型打出了公网缺口 |

### 8. 数据安全层 — 🟡 半档

| | 内容 |
|---|---|
| **叙述** | 本地备份（daily/weekly + sha256 manifest + 季度恢复演练）+ rclone/restic 异地推对象存储（README L270） |
| **现实** | `backup.sh`/`restore.sh` 真实且有离线测试（`test_backup_scripts.py`）、manifest 校验、pre-restore 快照，工程质量好。**但**：① 无 **RTO/RPO 定义**——daily cron 意味着 RPO≤24h、RTO 取决于人肉恢复速度，从未被写明；② `secrets/` 不在卷里，README L180-181 自述「手工纳入你的备份」——**凭证是恢复的必要条件，却落在备份机制之外**；③ 「建议每季度做一次恢复演练」（README L175）是建议不是制度——没有演练记录模板、没有日历化、没有验收标准 |
| **定级依据** | 备份的「备」做扎实了；「能不能恢复、多久恢复」的另一半完全是裸的 |

### 9. 发布层 — 🟡 半档

| | 内容 |
|---|---|
| **叙述** | CI → 镜像 push registry（不可变 tag 锚 git sha）→ 部署流水线 + 体检 → 按 tag 一键回滚；「GHCR 镜像同时是灾备存档」（README L271, L204） |
| **现实** | GHCR 流水线真实（`ci.yml:109-143`，双架构 + 不可变 tag + LABEL）。**但** `deploy.sh:49` 的实际动作是 `git checkout tag → compose build`——**目标机现场构建**，而非 pull GHCR 镜像：① 「GHCR 灾备存档」只在 `deploy.sh:12-13` 注释里以「手动顶上」形式存在，脚本主路径不消费它；② 现场构建使「部署产物 ≠ CI 验证产物」（CI build 过的镜像与服务器 rebuild 的镜像不保证逐字节一致，尽管 lockfile 收敛了大部分漂移）；③ `compose up -d` 同容器替换 = **带停机窗口的部署**，无蓝绿/金丝雀 |
| **定级依据** | 流水线存在且合格；但「部署走 registry 镜像」这一企业基线动作没有落地，灾备叙述与脚本行为有缝 |

### 10. 观测告警层 — ✅ 落地（最成熟的一层）

| | 内容 |
|---|---|
| **叙述** | OTel → collector → Langfuse + Prometheus/Grafana；Alertmanager → 飞书；死人开关 + run 卡死看门狗（exit 自愈）（README L272） |
| **现实** | 与叙述一致：9 个指标（`observability.py:150-172`）、8 条告警规则进 CI 校验（`ci.yml:60-65`）、飞书转译器、deadman ping、三层心跳 watchdog（`watchdog.py`）+ `os._exit(70)` 自愈（`watchdog.py:299-309`）。traceId 确定性约定有评审存档（`docs/research/2026-09-22-otel-critique-review.md`） |

**残余瑕疵**（不降级）：① 指标进程内存态重启清零（README 自述，口径诚实但意味着 Grafana 面板在重启后断档）；② 告警是**事件式**（某事发生了）而非 **SLO 式**（错误预算燃烧率）——因为 SLO 从未定义；③ watchdog `exit` 自愈依赖 compose `restart: unless-stopped`，裸跑/systemd 场景无对应资产。

## 批判结论

这套文档的最大优点是**诚实的主体**（出界项自列、json 档逐字节口径、瞬时一致性自认），最大问题是**少数关键处叙述溢出 + 安全关键动作无机制承载**。修订方向不是重写，而是：① 硬错误 E1–E7 就地修正；② 半档层的「依赖人工纪律」部分逐条转化为 ROADMAP 条目并标注；③ 全绿两层的残余瑕疵降级为演进项。批判②（质量属性横切）给出这些缺口对企业生产基线的风险定价，ROADMAP 给出清偿顺序。
