# 批判补遗：P1-1 落地过程中的两个发现（2026-09-25）

来源：P1-1（claimed_by 租约认领）实施前的代码走查。按纪律「新增缺口先登记批判再入表」。

## 发现① queued 状态从不落库（已随 P1-1 修复）

**实锤链**：`resolve_run` 落 `created`（graph.py:124）→ `_enqueue` 只写内存 `_TASKS`
（api.py）→ `_drive` 拿信号量才把 DB 翻 `running`。DB 里不存在 `queued` 态。

**后果**（全部已修复并钉入 test_pg_stores §6）：
- `counts()/total_active()/active_for()` 按 `status IN ('queued','running')` 计数 →
  排队项不计入 **QUEUE_MAX/USER_QUEUE_MAX 配额闸**（PG 档可无限堆排队 run）；
- `is_alive()` 跨副本 dedup 判活看不见排队项 → **同 URL 跨副本双投**；
- /queue 与观测 gauge 的 queued 段 PG 档恒 0（比 json 档读内存还差）；
- 单副本重启：排队项 DB 停在 created，恢复只认 running → **排队 run 永久丢失**。

**批判② R3「queued 态 run 无属主」的记载比实况浅**——不止租约缺失，是排队态在
DB 侧整体不可见。修复口径：`_enqueue` PG 档 `mark_queued`（翻 queued+钉名，直接
UPDATE 防 merge 覆盖 claimed_by）+ lifespan 常驻 `_queue_hb_loop` 排队心跳。

## 发现② recover_candidates 不看 claimed_by——B 重启可抢 A 活着的 run（未修，挂 P1-4）

**链路**：`recover_candidates`（pgstore.py）`SELECT ... WHERE status='running'
FOR UPDATE SKIP LOCKED`——不看 claimed_by 与 updated 租约。SKIP LOCKED 只互斥
「并发启动的两副本」（扫描窗口内持锁），**稳态下的副本 B 重启时会把健康副本 A 正在
驱动 的 running 行整批拿走重投** → 双副本同 run 并发驱动（checkpointer 幂等性是
「重入」语义，不是「并发写同一 thread」语义）。

**为何本批不修**：P1-1 的验收是租约到期接管（watchdog 路径）；恢复路径的抢活是
P4b 既有语义，动它需要「进程级存活信号」（cmd 通道 proc 心跳）设计，与 P1-4
真双进程冒烟同窗落地最合适——冒烟会直接暴露并钉住它。

**去向**：并入 ROADMAP P1-4 验收口径（见 ROADMAP P1-4 内容扩充）。
