# 设计决策

video2pdf 的核心是一条长耗时、强依赖外部服务（视频站、GPU、LLM）的管线。下面几条取舍决定了它在失败时的行为和成本。实现细节见 `backend/video2pdf/graph.py` 顶部注释与 `docs/architecture/`。

## 1. 长耗时阶段不做框架级重试

**决策**：下载、转写这类网络型阶段不挂 LangGraph `retry_policy`；重试只放在 `llm.chat` 内（默认 3 次，4xx 直接失败）。

**原因**：转写单次就要几十分钟 GPU 时间。框架级自动重试会把一次可预期的失败放大成几倍的算力账单，抵消掉熔断器省下的钱。LLM 调用便宜且偶发抖动常见，重试划算；GPU 阶段失败通常是配额或源站问题，重试大概率还是失败。

**代价**：偶发网络抖动会让一条任务失败，需要用户手动重试。因为状态逐条持久化，重试只补跑失败的部分。

## 2. LLM 连续三次失败，整条任务判错

**决策**：逐条目整理笔记时，LLM 连续三次失败就把整条任务判为 error，不再处理剩余条目；单个条目被质量门禁拒绝只记为 partial，继续下一条。

**原因**：要区分全局故障和个别坏数据。LLM 连续失败几乎都是端点、鉴权或额度出了问题，继续跑剩下的 50 条只会白白消耗前面阶段的产物和用户的等待时间。某一条视频转出空内容或被拒答，属于这条数据本身的问题，不应该拖垮整个合集。

**同一原则**：阶段熔断器（`V2PDF_CB_THRESHOLD`，默认 3）对“连续同因失败”生效。

## 3. GPU 不可用时默认明确失败，不悄悄降级

**决策**：T4 拿不到配额时默认直接报错；只有显式设置 `V2PDF_COLAB_CPU_FALLBACK=on` 才降级到 CPU。

**原因**：CPU 转写一个长视频可能要几个小时。悄悄降级会让用户看到“任务一直在跑”，体验比一个明确的错误更差，还会占住 worker 阻塞队列。是否接受慢速换成功，应该由部署者明确选择。

## 4. LLM 选帧失败时用本地评分兜底

**决策**：LLM 内容选帧失败或返回空结果时，回落到基于清晰度、场景切变和去重的本地启发式选帧。

**原因**：配图是笔记的增值部分，不是必需部分。选帧失败不应该阻断笔记产出；本地兜底质量略低，但零成本、确定性强。这一点和第 3 条相反：降级代价小、用户无感时自动降级，代价大时让人决定。

## 5. 质量门禁拦在写盘前

**决策**：写入 vault 前检查拒答、空内容、缺少有效转录本等情况，命中就拒绝写盘。

**原因**：文稿一旦交到用户手里，垃圾内容的清理成本由用户承担。宁可少产出一条，也不把不合格的内容交出去。

## 6. 幂等与可恢复

**决策**：以 URL 和视频指纹做幂等记录，每个条目写盘成功后立即落盘状态；checkpoint 的 `thread_id` 与 `run_id` 相同；任务成功后删除 checkpoint，失败任务保留以便排查。

**原因**：重复提交同一链接直接跳过，进程崩溃后从断点续跑，不重复付 GPU 和 LLM 的钱。成功后清理 checkpoint，防止磁盘只增不减。

## 7. 评测集来自线上真实失败

**决策**：把线上遇到的真实问题（平台风控、计费异常、人工审阅批注）沉淀为离线回归集，在 CI 中零 token 运行，见 `docs/evals/`。

**原因**：LLM 产品的回退往往不是代码报错，而是行为悄悄变差。把每次踩过的坑固化成用例，才能在改 prompt、换模型、改路由时快速发现回退。
